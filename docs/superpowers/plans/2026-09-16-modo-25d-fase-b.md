# Modo 2.5D · Fase B — terreno persistente y sincronizado

> **For agentic workers:** ejecutar tarea a tarea con un implementador fresco por tarea y una revisión (spec + calidad) después de cada una, como en la fase A. Cada tarea: test en rojo → código → verde → `npm run check` → commit. Las casillas `- [ ]` sirven para llevar el progreso.

**Goal:** El relieve, materiales, objetos, piezas de pared y fuentes de agua de una escena 2.5D viven en PostgreSQL, los edita el director con las herramientas Subir/Bajar/Pintar/Objeto/Agua, y todos los clientes conectados ven el mismo tablero.

**Architecture:** Un blob por escena (`terrain`), cargado en memoria con el tablero. Las ediciones viajan como mensaje WS `terrain` (op + `version`), el servidor las valida (`rules.js`), las aplica al blob en memoria, incrementa `version`, las reenvía y las vuelca con `flush()`. El cliente aplica localmente lo suyo y lo remoto; si su `version` se desfasa pide el terreno completo. El agua nunca viaja.

**Tech Stack:** Node 22, PostgreSQL 16 (bytea + jsonb), `node:test`, cliente clásico + módulos `public/js/d3/*`.

**Spec:** `docs/superpowers/specs/2026-09-16-modo-25d-design.md` (secciones «Decisiones», «Tiempo real», «Errores», «Tests»).

**Requisito previo:** fase A terminada (tareas 1–12 de `2026-09-16-modo-25d-fase-a.md`), en particular el troceo en módulos (`world.js`, `terrain.js`, `water.js`, `input.js`). Si el motor sigue en `engine.js`, terminar A primero.

## Global Constraints

- SQL sólo en `server/db.js`; validación y aplicación de ops en `server/rules.js` (funciones puras, testables sin red). `app.js` sólo enruta.
- Migración `005-terreno.sql` aditiva. Sin dependencias nuevas.
- Límites: `n` ∈ [22, 118] y par; `h` ∈ [0, 9]; `m` índice válido de `MATS` (0..6, ver `MATS` en `terrain.js`); ≤ 2000 celdas por op `cells`; `kind` de objeto en `OBJ_KINDS` (catálogo del motor, exportado también en un módulo puro compartido). Los mismos límites en cliente y servidor.
- `W` (agua) no se persiste ni viaja; `springs/sinks/evap/edgeDrain` sí (en `extras`).
- Jugadores: sólo `door` (según `playersDoors` y `locked`). Cualquier otra op de jugador → descartada + `fix`.
- Un tablero 2D no cambia en nada.
- Test primero; `npm run check` verde por commit; `npm run test:ui` antes de desplegar.

### Task B1: módulo puro `server/terrain.js` + migración 005 + consultas

**Files:** Create `server/migrations/005-terreno.sql`, `server/terrain.js`; Modify `server/db.js`; Test `test/terrain.test.js`, `test/db.test.js`.

**Interfaces (produce):**
```js
// server/terrain.js
const TERRAIN_LIMITS = { N_MIN: 22, N_MAX: 118, GROW_STEP: 8, H_MAX: 9, MAX_CELLS_PER_OP: 2000, MAX_SPRINGS: 64 };
const MATS   // [{key:'grass',...}] mismo orden que el motor
const OBJ_KINDS // {arbol:{move:1,sight:0,...}, puerta:{door:true,...}, ...} mismo contenido que el motor
function blankTerrain(n, h = 1, m = 0)           // → {n, h:Uint8Array, m:Uint8Array, extras:{objs:{}, mounts:{}, springs:[], sinks:[], evap:.0012, edgeDrain:true}, version:0}
function generate(kind)                          // 'valle' | 'cripta' → terreno como el diorama (sin three)
function encode(t)  // → {n, h:Buffer, m:Buffer, extras, version}
function decode(row)// fila de la tabla → terreno
function cleanTerrainOp(op)                      // → op saneada o null (rangos, tamaños, kinds)
function applyTerrainOp(t, op)                   // muta t, version++; devuelve {changed:true} o lanza si op inválida contra ese terreno (p. ej. grow > N_MAX)
```
`generate('valle')` se porta desde `diorama-jav/index.html` `SCENES.valle.build` (líneas 1375–1470 del original; en el motor ya troceado, `world.js`): sólo lógica de alturas/materiales/objetos/manantiales; los personajes y luces de la demo **no** entran (son fase C).

Migración:
```sql
CREATE TABLE terrain (
  scene_id   TEXT PRIMARY KEY REFERENCES scenes(id) ON DELETE CASCADE,
  n          INTEGER NOT NULL,
  h          BYTEA   NOT NULL,
  m          BYTEA   NOT NULL,
  extras     JSONB   NOT NULL DEFAULT '{}'::jsonb,
  version    INTEGER NOT NULL DEFAULT 0,
  updated_at BIGINT  NOT NULL
);
```
`db.js`: `terrain: (sceneId) => one('SELECT scene_id, n, h, m, extras, version FROM terrain WHERE scene_id = $1', [sceneId])`, `upsertTerrain: (sceneId, t) => run('INSERT … ON CONFLICT (scene_id) DO UPDATE SET n=EXCLUDED.n, h=EXCLUDED.h, m=EXCLUDED.m, extras=EXCLUDED.extras, version=EXCLUDED.version, updated_at=EXCLUDED.updated_at', …)`, `deleteTerrain`.

- [x] Tests (rojo): `blankTerrain(22)` → 484 bytes por columna; `generate('valle').n===22` y tiene ≥1 manantial y ≥1 desagüe; `cleanTerrainOp({type:'cells',cells:[{i:0,h:12}]})` → `h` recortado a 9; `cells` con 2001 entradas → null; `obj` con `kind:'dragon'` → null; `applyTerrainOp(grow)` con `n=118` → lanza; `encode/decode` ida y vuelta idéntica; `db`: `upsertTerrain` + `terrain` devuelven lo mismo; borrar la escena borra el terreno (cascade).
- [x] Implementar. - [x] `npm run check`. - [x] Commit `feat(2.5d): módulo de terreno puro, migración 005 y consultas`.

### Task B3: servidor — carga, estado, `handleTerrain`, volcado

**Files:** Modify `server/app.js` (`makeScene`, `openBoard`, `stateFor`, `flush`, `handleMessage` switch, `create` de escena, `createBoard` en db.js); Test `test/realtime.test.js`, `test/api.test.js`.

**Comportamiento:**
- `openBoard`: para tableros `mode==='2.5d'`, cada escena carga `sc.terrain = decode(row) || generate('valle')` (si no existe fila: se crea al vuelo y se marca `terrainDirty`).
- `createBoard(name, owner, '2.5d')` inserta `generate('valle')` para la primera escena; `scene create` en 2.5D inserta `blankTerrain(22)`.
- `stateFor`: si 2.5D, `terrain: { n, h: base64, m: base64, extras, version }` de la escena del cliente.
- Mensaje `{t:'terrain', scene, op}`: cola por tablero como los demás. `cleanTerrainOp` → null ⇒ `fix` al emisor (`{t:'terrain', fix:true, full:<terreno>}`). `terrainOpAllowed` falso ⇒ igual. Si `op.version !== sc.terrain.version` ⇒ responder `full` (sin aplicar). Si ok: `applyTerrainOp`, `sc.terrainDirty=true`, broadcast `{t:'terrain', scene, op, version}` a los demás de esa escena y `{t:'terrain', ack:true, version}` al emisor.
- `{t:'terrain', scene, want:'full'}` ⇒ responder `full`.
- `flush`: si `sc.terrainDirty`, `t.upsertTerrain(sc.id, encode(sc.terrain))` en la misma transacción.
- `fx` (para fase E): `{t:'terrain', fx:{cell,level}}` se reenvía tal cual a los demás sin tocar el blob (dejarlo previsto, sin test aún).

- [x] Tests (rojo): estado de un tablero 2.5D trae `terrain.n===22`; gm envía `cells` → otro cliente recibe `op` con `version` 1; tras `close` de todos y reconectar, la altura persiste (fila en `terrain`); jugador envía `cells` → recibe `fix`, el gm no recibe nada (`silence`); `door` de jugador con `playersDoors` abre para todos; op con `version` vieja → `full`; tablero 2D: `stateFor` sin `terrain` y `handleTerrain` ignora.
- [x] Implementar → verde → commit `feat(2.5d): terreno en el estado, ops terrain y volcado`.
